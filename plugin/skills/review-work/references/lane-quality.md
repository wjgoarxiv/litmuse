# Lane 3: quality

Question: is the implementation correct, maintainable, tested and packaged in the repo's own idiom?

Agent: `litmuse/quality-reviewer` (tools `read_file`, `search`). The parent supplies the diff, full text of the
changed files and the neighbors that show established patterns, because the agent cannot run git or tests.

Standard: would the maintainer approve this pull request without comments?

## Dimensions

1. **Correctness.** Logic errors, off-by-one, null and undefined handling, race conditions, resource leaks,
   unhandled promise rejections, wrong units, ordering assumptions.
2. **Pattern consistency.** New code follows the codebase's established patterns, judged against the neighboring
   files. A second way of doing something the repo already does one way is a finding.
3. **Naming and readability.** Names say what things are; another engineer understands the code without a
   walkthrough.
4. **Error handling.** Errors are caught where they can be handled, logged once, propagated with context, and
   shown to users in helpful terms. Empty catch blocks and swallowed errors are findings.
5. **Type safety.** Casts to `any`, ignore directives, loose generics, missing narrowing (typed languages).
6. **Performance.** N+1 access, blocking I/O on hot paths, unbounded growth, needless re-renders or re-reads.
7. **Abstraction level.** No copy-paste duplication, and no premature layers either.
7a. **Minimum-first fit.** Existing helpers, the standard library, native platform features or installed
   dependencies should do the job before custom code. Avoidable helpers, layers, config, tests and docs are
   findings.
8. **Testing.** New behavior has a test that fails without the change; tests describe scenarios in their names;
   removed or skipped tests are justified; no `.only`, no skip flags added to green a suite.
9. **API design.** Public interfaces are consistent with existing ones; breaking changes are flagged and versioned
   in the way the repo does it.
10. **Tech debt.** New coupling, hidden global state, TODOs with no owner.

## Package and payload

For anything that ships:

- Pack listing: `npm pack --dry-run --json --ignore-scripts`, read `[0].files` (the human listing wraps long paths
  and corrupts a diff). New files are included, working state and local ledgers are excluded, and a pinned fixture
  of the listing, when the repo keeps one, matches.
- Manifests and lockfiles agree; versions move in lockstep across `package.json`, plugin manifests and changelog,
  and only with approval.
- Generated hashes, digests and payload pins are regenerated by the documented command, never edited by hand.
- Docs, help text and changelog describe the new behavior and nothing the code lacks.
- File size, naming and structure match the repo's conventions; no stray edits outside scope; no unrelated
  refactors.

## Muse-specific checks (plugin repos)

Skill folders match the manifest and route table, descriptions fit the byte cap, hook digests are synced,
`muse plugins validate` is clean, reference closure holds (every relative path a skill names exists).

## Severity mapping

| Child word | Common scale |
| --- | --- |
| CRITICAL | BLOCKER |
| MAJOR | MAJOR |
| MINOR | MINOR |
| NITPICK | NOTE |

A style preference is never above MINOR.

## Return shape

```text
verdict: PASS | FAIL | BLOCKED
confidence: HIGH | MEDIUM | LOW
summary: ...
findings:
  - [CRITICAL|MAJOR|MINOR|NITPICK] category - path:line - current - suggestion
blocking_issues: CRITICAL and MAJOR only
```

## Sample brief

```text
TASK: Review lane 3 (quality) of the diff in .litmuse/evidence/<slug>/review/diff.patch.
SCOPE: read-only; changed files plus neighbors listed in context.txt under PATTERN_FILES.
DELIVERABLE: the return shape. Anchor every finding to path:line and give a concrete suggestion.
VERIFY: for each finding, quote the shortest code fragment that shows it.
STOP WHEN: all ten dimensions have been examined and the schema is returned.
```
